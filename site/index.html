PHP Kwetsbaarheid

Twee kritieke lekken in PHP. De patch komt vandaag om 16:00. Tot die tijd: niet in paniek raken, wel PHP uitzetten.

16:0021 oktober, Nederlandse tijd (14:00 UTC): de geplande release van de gepatchte PHP-versies. Mogelijk eerder.

Huidig crisusniveau: 4 van 5

Wat is er aan de hand?

Het lek
Twee kritieke kwetsbaarheden in PHP zelf: CVE-2026-109618 en CVE-2026-109619, ook wel “php2shell”. Elk lek met een bijnaam is erger dan een lek zonder.
Ernst
CVSS v4.0: 9,2 voor allebei. Ter vergelijking: een tien is het maximum. Een negen is “laat alles vallen”.
Wat kan een aanvaller?
Met een eenvoudig POST-verzoek eigen code uitvoeren op uw server (remote code execution). Daarna is het hun server.
Welke versies?
In elk geval alle versies vanaf PHP 5. Daarmee is alles waar PHP in zit vermoedelijk kwetsbaar: WordPress, Joomla, Drupal, Zabbix, Roundcube, maar ook de beheerpagina van uw router, NAS of printer.
Misbruik?
Er is een openbare proof of concept. Cloudflare zegt al aanvallen te zien. Het NCSC en de PHP Foundation zien nog geen actief misbruik. Ga ervan uit dat Cloudflare gelijk heeft.
Hoe groot?
Ongeveer 70 procent van alle websites draait op PHP. Ook de uwe, waarschijnlijk. Ook als u denkt van niet.
De patch
Woensdag 21 oktober, 16:00 Nederlandse tijd (14:00 UTC). Mogelijk eerder, als de details eerder op straat liggen. Voor zover bekend alleen voor PHP 8. Draait u PHP 7 of ouder? Dan komt er voor u geen patch. Alleen een upgrade.

Wat moet u doen?

Ga naar binnen. Sluit ramen en poorten. Zet PHP uit.

  1. Zoek uit waar u PHP draait. Ook op plekken waar u het niet verwacht. 
    php -v
dpkg -l | grep -i php        # Debian, Ubuntu
rpm -qa | grep -i php        # Fedora, RHEL, openSUSE
  2. Kunt u niet wachten tot 16:00? Zet PHP tijdelijk uit. Statische pagina's blijven gewoon werken. Voor Apache, bijvoorbeeld in een eigen conf: 
    # Elk verzoek dat bij een PHP-bestand uitkomt krijgt een 503,
# vóór PHP het ziet. Laat mod_php geladen, anders ziet
# de bezoeker uw broncode.
<If "%{REQUEST_FILENAME} =~ m#\.(php[0-9]?|phtml|phar)$#i">
    Redirect 503
</If>
    Voor nginx, bóven uw bestaande PHP-blok: 
    location ~* \.(php[0-9]?|phtml|phar)$ { return 503; }
    Gebruikt u PHP-FPM? Zet de dienst dan ook stil: systemctl stop php8.4-fpm.
    Zit u achter Cloudflare? Hun firewallregels staan aan, ook voor gratis klanten. Cloudflare noemt het zelf “a stopgap only”. Een noodverband dus. Patchen moet nog steeds.
  3. Om 16:00: patchen. Wacht op de pakketten van uw distributie (zie is de patch er al voor mij?). Installeer ze zodra ze er zijn: 
    sudo apt update
sudo apt install --only-upgrade $(dpkg -l | awk '/^ii  (lib)?php/{print $2}')
sudo systemctl restart apache2 php8.4-fpm   # of wat u draait
    Controleer met php -v dat u echt de nieuwe versie draait. Zet daarna pas PHP weer aan.
  4. Draait u PHP 7 of ouder? Upgrade naar PHP 8. Er komt geen patch. Ook niet als u het heel lief vraagt.
  5. Kijk terug. Zoek in uw logs naar vreemde POST-verzoeken van de afgelopen dagen. Vindt u iets? Ga er dan van uit dat de server niet meer van u is.
  6. Klik niet op links in e-mails over dit lek. Wij mailen nooit. Wij kunnen ook niet mailen: onze webmail draait op PHP.

Is de patch er al voor mij?

De fix verschijnt om 16:00 op php.net. Daarna bouwt uw distributie eigen pakketten. Dat duurt uren, soms dagen.

Let op: distributies backporten. Debian en Red Hat zetten de fix vaak in hun eigen versie, zonder het versienummer van php.net over te nemen. Vergelijk dus niet uw php -v met php.net. Zoek de CVE-nummers in de changelog van uw pakket. Staan ze erin, dan zit de fix erin.

De CVE-pagina’s van de distributies hieronder kunnen tot na de release een 404 geven. Dat is geen goed nieuws. Het is helemaal geen nieuws.

Debian, Raspberry Pi OS apt 
sudo apt update
apt list --upgradable 2>/dev/null | grep -i php
apt changelog php8.4 | grep -m3 -E 'CVE-2026-10961[89]'   # Debian 12: php8.2

Geeft de laatste regel de CVE-nummers? Dan is de fix er. Installeer hem met sudo apt upgrade. Volg de Debian security tracker en de DSA’s.

PHP van packages.sury.org? Dan komt de fix van Ondřej Surý, niet van Debian. Kijk met apt-cache policy php8.4 waar uw PHP vandaan komt.

Ubuntu apt, pro 
sudo apt update
apt list --upgradable 2>/dev/null | grep -i php
sudo pro fix CVE-2026-109618
sudo pro fix CVE-2026-109619

pro fix zegt of uw systeem kwetsbaar is. Is de fix er, dan installeert hij hem meteen. Ubuntu geeft het lek de prioriteit Critical. Status per release: ubuntu.com/security/CVE-2026-109618.

Ubuntu 22.04 of ouder draait PHP 8.1 of 7.x. Fixes komen daar alleen via Ubuntu Pro, als ze komen. PHP uit de PPA ondrej/php? Dan komt de fix van de PPA.

RHEL, AlmaLinux, Rocky, CentOS Stream, Fedora dnf 
sudo dnf check-update 'php*'
sudo dnf updateinfo list --cve CVE-2026-109618     # RHEL en klonen
rpm -q --changelog php-cli | grep -m3 CVE-2026-10961   # na de update

Fedora volgt php.net op de voet: daar mag u het versienummer wel vergelijken. Red Hat publiceert de status op de CVE-pagina. PHP uit de Remi-repository? Dan komt de fix van Remi. Meestal snel.

openSUSE, SLES zypper 
sudo zypper refresh
zypper list-patches --cve=CVE-2026-109618
zypper list-patches --cve=CVE-2026-109619
sudo zypper patch --cve=CVE-2026-109618

Tumbleweed werkt zonder patches: zypper lu | grep -i php en daarna sudo zypper dup. Status: SUSE CVE-pagina.

Alpine, Arch apk, pacman 
# Alpine
apk update
apk version -l '<' | grep -i php
# Arch (checkupdates zit in pacman-contrib)
checkupdates | grep -i php
sudo pacman -Syu

Arch is rolling: pacman -Syu en klaar. Dat wist u al. U gebruikt immers Arch.

Docker officiële php-images 
docker pull php:8.4-apache
docker run --rm php:8.4-apache php -v
docker build --pull --no-cache -t mijn-app .   # eigen image

De officiële images volgen php.net, meestal binnen enkele uren. Vergelijk php -v met de versie op php.net. Een container die al draait, blijft oud. Maak hem opnieuw aan. Een herstart is niet genoeg.

Windows IIS, XAMPP, WampServer, Laragon 
php -v
choco outdated            # Chocolatey
choco upgrade php
scoop status              # Scoop
scoop update php
iisreset                  # IIS met FastCGI

Windows-builds staan op windows.php.net, meestal snel na de release. Vergelijk ze met uw php -v. Handmatig? Pak de nieuwe zip uit over uw PHP-map. Bewaar uw php.ini.

XAMPP, WampServer en Laragon lopen vaak achter. Vervang de PHP-map dan zelf. Staat XAMPP open naar internet? Dan heeft u twee problemen.

macOS Homebrew, MacPorts, Herd, MAMP 
brew update
brew outdated | grep -i php
brew upgrade php                 # of php@8.3
brew services restart php
sudo port selfupdate && port outdated | grep -i php   # MacPorts

macOS heeft sinds Monterey zelf geen PHP meer. Heeft u PHP, dan heeft u het zelf geïnstalleerd. Laravel Herd en MAMP werkt u bij in de app. Die lopen soms een paar dagen achter.

Hosting, beheerpanelen, apparaten cPanel, Plesk, NAS, router

Shared hosting, cPanel, Plesk of DirectAdmin: de update komt van uw hoster of paneel. Vraag uw hoster wanneer. Vraag het niet om 15:59.

NAS, router, firewall of printer met een webinterface: wacht op firmware van de fabrikant. Tot die tijd hoort die beheerpagina niet aan internet. Eigenlijk hoort hij daar nooit.

Draait de nieuwe versie echt?

Een geïnstalleerd pakket is nog geen draaiend pakket. PHP-FPM en Apache houden de oude code in het geheugen tot u ze herstart.

php -v                         # de CLI
php-fpm8.4 -v                  # FPM is een apart programma (RHEL: php-fpm -v)
sudo needrestart -r l          # Debian, Ubuntu: wat draait nog oude code?
sudo dnf needs-restarting -s   # RHEL, Fedora
sudo zypper ps -s              # openSUSE
curl -sI https://uw-site.nl | grep -i x-powered-by

Toont die laatste regel een versienummer? Dan vertelt u het ook aan aanvallers. Zet expose_php = Off in uw php.ini.

Pas als de CVE in de changelog staat en de dienst herstart is, bent u veilig. Zet dan pas PHP weer aan.

Updates

Uit voorzorg offline: de sites van DigiD en MijnOverheid, RTL, de KNVB, de Unie van Waterschappen, een rij ziekenhuizen en de vluchtinformatie in de Schiphol-app. In België gaan alle Vlaamse overheidssites op zwart, net als Smartschool.   2. 21 oktober 15:07

    Het NCSC noemt het lek “geen aanval, maar een weeffout in de software”. Ze roepen iedereen op de update direct te installeren: “elke minuut telt”. Wij noemen de weeffout voortaan PHP.

  3. 21 oktober 14:07

    Cloudflare ziet al aanvallen en zet firewallregels aan voor al zijn klanten. Het NCSC en de PHP Foundation zien nog geen misbruik. Eén van de drie heeft het mis. Wij gaan uit van het ergste. Dat is ons vak.

  4. 21 oktober 14:45

    De status is ongewijzigd. Er wordt gewacht op de patch. Het crisusteam staat paraat met apt upgrade al half getypt.

    Het NCSC heeft zijn eigen website uit voorzorg offline gehaald. Wij hebben uit solidariteit overwogen hetzelfde te doen, maar crisus.nl draait geen PHP. Dus nee.

  5. 21 oktober 13:59

    Het NCSC waarschuwt: bereid u voor op patchen. Er is een openbare proof of concept, maar nog geen actief misbruik. Alle versies vanaf PHP 5 zijn kwetsbaar. Zie de advisory.

  6. 21 oktober 13:00

    Meerdere diensten zijn nog preventief offline. Het netwerk werkt wel. De koffieautomaat draait geen PHP en is dus beschikbaar. Uit voorzorg is hij toch alvast leeggedronken.

  7. 21 oktober 12:15

    Het crisusteam heeft overlegd over de agenda van het volgende crisusoverleg. Er komt een werkgroep. De werkgroep heeft een Signal-groep. De Signal-groep heeft 214 ongelezen berichten, waarvan 190 stickers.

  8. 21 oktober 09:30

    Uit voorzorg staat PHP uit. Alles wat geen PHP is, werkt gewoon. Dat blijkt verrassend veel te zijn. Er komt een onderzoek naar de vraag waarom we eigenlijk nog PHP hebben.

  9. 20 oktober 21:35

    Details over de lekken liggen al op straat, de CVE-nummers ook. Dat was niet de bedoeling. Het is wel precies wat lekken doen.

  10. 20 oktober

    Het PHP-beveiligingsteam kondigt een kritieke beveiligingsrelease aan voor woensdag 21 oktober, 14:00 UTC. Twee lekken, allebei CVSS 9,2. Details volgen bij de release. Iedereen gaat slapen. Niemand slaapt.
