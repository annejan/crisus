Wat is er aan de hand?

Het lek
Twee kritieke kwetsbaarheden in PHP zelf: CVE-2026-109618 en CVE-2026-109619, ook wel “php2shell”. Elk lek met een bijnaam is erger dan een lek zonder.
Hoe werkt het?
CVE-2026-109618, “RCE via OOM corruption”: bij een geheugentekort springt PHP met longjmp() uit een request. Soms staat het geheugen dan half klaar. Het afsluiten van het request leest dat daarna toch. Een aanvaller dwingt dat tekort af met een slimme multipart-POST, nog voordat uw eigen code draait. Volgens de write-up van de vinders op twee manieren. Eén: PHP toetst post_max_size aan de opgegeven Content-Length, niet aan wat er echt binnenkomt. Een chunked verzoek zonder lengte glipt erlangs. Twee: een lege upload (filename="") telt niet mee voor max_file_uploads, maar maakt wel zes $_FILES-items aan. Met geneste veldnamen als files[a][b][c] blaast een body van minder dan 8 MiB de standaardheap van 128 MiB op.

CVE-2026-109619, “RCE via stale global state”: globale toestand van het ene request wijst nog naar vrijgegeven geheugen als het volgende request op dezelfde worker begint. Een use-after-free. Twee verzoeken na elkaar zijn genoeg.
Welke opzet?
Apache met mod_php: volledige RCE bevestigd voor allebei, met de standaardinstellingen. PHP-FPM: RCE bevestigd via de sessievariant van CVE-2026-109619. FrankenPHP en LSAPI zijn volgens PHP vermoedelijk ook kwetsbaar.
Ernst
CVSS v4.0: 9,2 voor allebei. Ter vergelijking: een tien is het maximum. Een negen is “laat alles vallen”.
Wat kan een aanvaller?
Met een eenvoudig POST-verzoek eigen code uitvoeren op uw server (remote code execution). Daarna is het hun server.
Welke versies?
Alles vanaf PHP 5.4.0, en met de standaardinstellingen altijd uit te buiten. De vinders bevestigen RCE zonder inloggen op WordPress, Drupal, Joomla, MediaWiki, Roundcube, Magento, phpMyAdmin, Nextcloud, Laravel, Symfony en WHMCS. Staat uw favoriet er niet bij? Dan is hij niet getest. Niet veilig.
Wie vond het?
Calif, OpenAI en Wiz, samen met de PHP Foundation. De basis is oud. Stefan Esser vond in 2004 al een RCE via de geheugenlimiet. In 2020 meldde iemand het geheugentekort als bug #78876. In 2024 vond een audit het opnieuw. Niet gefixt: uitbuiting was “niet bewezen”. Inmiddels wel.
Misbruik?
Er is een openbare proof of concept. Cloudflare zegt al aanvallen te zien. Het NCSC en de PHP Foundation zien nog geen actief misbruik. Ga ervan uit dat Cloudflare gelijk heeft.
Hoe groot?
Ongeveer 70 procent van alle websites draait op PHP. Ook de uwe, waarschijnlijk. Ook als u denkt van niet.
De patch
Uit sinds 21 oktober 15:34. Gefixt in 8.5.12, 8.4.27, 8.3.36 en 8.2.35. Elke oudere versie is kwetsbaar. PHP 8.1, 8.0 of 7.4? Daarvoor komt geen release. Wel heeft het PHP-team voor 7.4, 8.0 en 8.1 een “minimal mitigation for EOL version” als branch op GitHub gezet. Die moet u zelf bouwen. PHP 7.3 of ouder? Dan is er niets. Alleen een upgrade.

Wat moet u doen?

Ga naar binnen. Sluit ramen en poorten. Zet PHP uit.

  1. Zoek uit waar u PHP draait. Ook op plekken waar u het niet verwacht. 
    php -v
dpkg -l | grep -i php        # Debian, Ubuntu
rpm -qa | grep -i php        # Fedora, RHEL, openSUSE
  2. Is er nog geen pakket voor u? Zet PHP tijdelijk uit. Statische pagina's blijven gewoon werken. Voor Apache, bijvoorbeeld in een eigen conf: 
    # Elk verzoek dat bij een PHP-bestand uitkomt krijgt een 503,
# vóór PHP het ziet. Laat mod_php geladen, anders ziet
# de bezoeker uw broncode.
<If "%{REQUEST_FILENAME} =~ m#\.(php[0-9]?|phtml|phar)$#i">
    Redirect 503
</If>
    Voor nginx, bóven uw bestaande PHP-blok: 
    location ~* \.(php[0-9]?|phtml|phar)$ { return 503; }
    Gebruikt u PHP-FPM? Zet de dienst dan ook stil: systemctl stop php8.4-fpm.
    Zit u achter Cloudflare? Hun firewallregels staan aan, ook voor gratis klanten. Cloudflare noemt het zelf “a stopgap only”. Een noodverband dus. Patchen moet nog steeds.
    Kan PHP echt niet uit? PHP zelf noemt deze noodmaatregelen. Ze dichten het lek niet helemaal. Zet ze in php.ini of de FPM-pool, niet per site, en herstart daarna elke worker: 
    memory_limit = -1                   # CVE-2026-109618; begrens geheugen dan via cgroup of container
session.upload_progress.enabled = 0 # CVE-2026-109619, sessievariant; ook na de patch verstandig
fatal_error_backtraces = 0          # CVE-2026-109619, alleen PHP 8.5
    Begrens de body al in de webserver: LimitRequestBody 8388608 in Apache, client_max_body_size 8m; in nginx, of wat uw eigen post_max_size is. Die tellen de bytes die echt binnenkomen, ook bij chunked. Dat stopt truc één, niet truc twee. Gebruikt uw site geen bestandsuploads of multipart-formulieren? Blokkeer multipart/form-data dan al vóór PHP.
  3. Nu: patchen. Neem de pakketten van uw distributie (zie is de patch er al voor mij?). Debian 13 heeft ze al. Installeer ze zodra ze er zijn: 
    sudo apt update
sudo apt install --only-upgrade $(dpkg -l | awk '/^ii  (lib)?php/{print $2}')
sudo systemctl restart apache2 php8.4-fpm   # of wat u draait
    Controleer met php -v dat u echt de nieuwe versie draait: 8.5.12, 8.4.27, 8.3.36, 8.2.35 of een distributiepakket met de CVE’s in de changelog. Zet daarna pas PHP weer aan.
  4. Draait u PHP 8.1 of ouder? Upgrade naar PHP 8.2 of nieuwer. Voor 7.4, 8.0 en 8.1 staat er een minimale fix op GitHub: zelf compileren, zelf testen, zelf verantwoordelijk. Wij zeiden eerder “ook niet als u het heel lief vraagt”. Blijkbaar heeft iemand het heel lief gevraagd. PHP 7.3 of ouder: echt niets.
  5. Kijk terug. Zoek in uw logs naar vreemde POST-verzoeken van de afgelopen dagen. Vindt u iets? Ga er dan van uit dat de server niet meer van u is.
  6. Klik niet op links in e-mails over dit lek. Wij mailen nooit. Wij kunnen ook niet mailen: onze webmail draait op PHP.

Is de patch er al voor mij?

De fix staat sinds 15:34 op php.net: 8.5.12, 8.4.27, 8.3.36 en 8.2.35. Nu bouwen de distributies hun pakketten. Dat duurt uren, soms dagen. De buildbots draaien. Wij kijken mee.

Let op: distributies backporten. Debian en Red Hat zetten de fix vaak in hun eigen versie, zonder het versienummer van php.net over te nemen. Vergelijk dus niet uw php -v met php.net. Zoek de CVE-nummers in de changelog van uw pakket. Staan ze erin, dan zit de fix erin.

De CVE-pagina’s van de distributies hieronder kunnen nog even een 404 geven. Dat is geen goed nieuws. Het is helemaal geen nieuws.

Draait de nieuwe versie echt?

Een geïnstalleerd pakket is nog geen draaiend pakket. PHP-FPM en Apache houden de oude code in het geheugen tot u ze herstart.

php -v                         # de CLI
php-fpm8.4 -v                  # FPM is een apart programma (RHEL: php-fpm -v)
sudo needrestart -r l          # Debian, Ubuntu: wat draait nog oude code?

sudo zypper ps -s              # openSUSE
curl -sI https://uw-site.nl | grep -i x-powered-by

Toont die laatste regel een versienummer? Dan vertelt u het ook aan aanvallers. Zet expose_php = Off in uw php.ini.
